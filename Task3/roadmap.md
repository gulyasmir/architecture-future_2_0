# Roadmap трансформации данных для "Будущее 2.0"

## 1–3 месяц: Проектирование.

#### Основные задачи:

* **Проектирование новой архитектуры**: микросервисы, новая шина событий, новый DWH.
* **Определение доменов**: Медицина, Финансы, ИИ, Аптеки, Электроника.
* **Разработка витрины данных (Data Mart Portal)**: ТЗ, UI/UX-прототипы.
* **Пилотный разбор данных в BI**: выносим часть отчётов из старого DWH в новую витрину.

#### Технологии:

* Для шины событий: **Kafka / RabbitMQ**
* Для нового хранилища: **PostgreSQL / Snowflake / BigQuery**
* Для портала: **NestJS + Next.js + GraphQL / REST API**

#### **Результаты**:

* Спроектирована целевая архитектура (домены, микросервисы, события)
* Утверждён новый стек (Node.js/NestJS, PostgreSQL, Kafka, Next.js)
* Разработаны первые прототипы Data Mart Portal

#### **Ответственные команды**:

* Архитекторы
* Техлиды доменных команд

#### **Ресурсы**:

* Рабочее время архитекторов и senior-разработчиков
* Сервера под пилотное окружение
* Лицензии / доступы (Kafka, PostgreSQL, GitHub)

### Почему нужен этот этап:

* **Заложить правильный фундамент** новой архитектуры: если неправильно определить домены и слои архитектуры сразу, дальше изменения будут крайне дорогими и сложными.
* **Разграничить бизнес-ответственность**: домены (Медицина, Финансы, ИИ и т.д.) позволяют независимо масштабировать бизнес-направления.
* **Запустить первую итерацию витрины данных**: даже на базе старого DWH — чтобы сразу показать бизнесу ценность новой аналитики.
* **Определить стеки технологий**: чтобы все команды работали в унифицированной экосистеме, избежать разрозненности решений.

### Что это даёт бизнесу:

* Минимизация рисков ошибок на старте.
* Быстрая демонстрация первой ценности для пользователей и аналитиков.
* Понятная дорожная карта для инвестиций и ресурсов.

## 4–6 месяц: Построение инфраструктуры.

#### Основные задачи:

* **Миграция основных данных из SQL Server 2008 в новое хранилище** (без медданных пока).
* **Разделение данных по доменам**:

  * Медицинские данные отдельно.
  * Финансовые отдельно.
  * Административные отдельно.
* **Интеграция новой шины событий** для общения между микросервисами.
* Начинаем **развёртывание витрины данных** в тестовом контуре.

#### **Результаты**:

* Развёрнут новый PostgreSQL DWH
* Развёрнута Kafka или RabbitMQ
* Перенесены ключевые таблицы для финансов и клиентских данных
* Начата миграция отчётов в Power BI на новый источник

#### **Ответственные команды**:

* Команда Базы Данных
* Команда Интеграций

#### **Ресурсы**:

* DevOps для развёртывания брокера событий
* DBA-специалисты для миграции схем
* BI-аналитики для настройки новых отчётов

### Почему нужен этот этап:

* **Нужно избавиться от узкого места — старого SQL Server 2008**: он не справляется с объёмами, не масштабируется и тормозит аналитику.
* **Разделение данных по доменам** повышает безопасность и ускоряет доступ к данным (например, персональные медданные будут изолированы от финансовых).
* **Шина событий** нужна для масштабируемой интеграции сервисов: Event-driven архитектура позволяет подключать новых игроков без перекомпиляции монолита.

### Что это даёт бизнесу:

* Значительное ускорение скорости отчётности.
* Возможность быстрого подключения новых направлений бизнеса (фармацевтика, электроника).
* Снижение затрат на поддержку старого кода и инфраструктуры.

## 7–9 месяц: Миграция микросервисов и логики.

#### Основные задачи:

* **Вынесение бизнес-логики в отдельные микросервисы** (на Node.js/NestJS).
* **Подключение новых бизнесов** (фармацевтические компании, производители электроники) через новую интеграционную шину.
* **Активация Data Mart Portal** для реальных пользователей.
* **Запуск self-service аналитики** в BI-системе (например, через Power BI + прямое подключение к Data Mart).
* **Пилотная эксплуатация новой архитектуры** в клиниках и финтех-подразделениях.

#### **Результаты**:

* Вынесена бизнес-логика из старого SQL DWH в отдельные микросервисы
* Data Mart Portal доступен для пилотных бизнес-пользователей
* Внешние интеграции через API Gateway + Event Bus

#### **Ответственные команды**:

* Backend команда микросервисов
* Frontend команда Portala
* Команда безопасности (для API)

#### **Ресурсы**:

* Расширение Kubernetes-кластера
* Мониторинг и логирование (Prometheus, Grafana)

### Почему нужен этот этап:

* **Вынос бизнес-логики из DWH**: монолитный DWH превращается в чистое аналитическое хранилище без тяжёлой бизнес-логики.
* **Подключение новых бизнесов** на новую инфраструктуру без доработок старых систем.
* **Запуск Data Mart Portal** в реальном бою: пользователи сами смогут собирать нужные отчёты, что разгружает IT-команды.
* **Тестирование всех новых процессов в реальной работе** до масштабного выката.

### Что это даёт бизнесу:

* Ускорение Time-To-Market новых продуктов.
* Повышение прозрачности и самостоятельности бизнес-пользователей.
* Снижение нагрузки на техподдержку и разработку.

## 10–12 месяц: Завершение миграции и масштабирование.

#### Основные задачи:

* **Финальная миграция всех критичных данных** в новые системы.
* **Миграция легаси интерфейсов** (по желанию — переписать Power Builder-интерфейс на современный фронт + API).
* **Отключение старого DWH** (минимизация поддержки старого SQL Server).
* **Формирование новых регламентов безопасности и доступа** для новой архитектуры.

#### **Результаты**:

* Завершена миграция всех критичных данных
* Отключен SQL Server 2008 и Apache Camel
* Data Lake введён в эксплуатацию для ИИ и аналитики
* Полный запуск новой витрины данных

#### **Ответственные команды**:

* Все доменные команды (медицина, финансы, аптеки, электроника)
* Отдел поддержки инфраструктуры

#### **Ресурсы**:

* Серверные мощности для хранения больших данных
* Бюджет на лицензии Snowflake/BigQuery (если будет выбрано)

### Почему нужен этот этап:

* **Закрытие долгов по миграции**: полный переход на новые сервисы и базы данных.
* **Отключение легаси-систем** (SQL Server 2008, Power Builder интерфейсы, Apache Camel), что уменьшает расходы на поддержку и инфраструктуру.
* **Ввод Data Lake**: нужен для хранения больших объёмов данных (например, изображений, медицинских данных для ИИ-анализа).
* **Финальная оптимизация** безопасности, политик доступа и мониторинга.

### Что это даёт бизнесу:

* Существенное снижение расходов на инфраструктуру.
* Устойчивость платформы к росту данных в будущем.
* Возможность более гибко работать с большими данными (Big Data, Machine Learning).
* Полная бизнес-автономия без риска "провала" старых систем.

## Конечная цель через 12 месяцев:

Бизнес-пользователи сами строят отчёты через удобный портал.

Все ключевые данные лежат в современной, масштабируемой инфраструктуре.

Новые компании интегрируются быстро и без дописывания монолитной логики.

Минимизированы риски легаси, старых систем и зависимостей.

## Краткий итог:
